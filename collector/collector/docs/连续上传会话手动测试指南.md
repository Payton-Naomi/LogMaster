# LogMaster 连续上传会话手动测试指南

## 1. 文档目的

本文用于手动验收以下功能：

- 开启云端上传时，项目、版本和上传人为必填项。
- 保存上传配置时创建云端上传会话并返回查询码。
- 同一串口连续产生的多个日志批次使用同一个查询码。
- 暂停、断开恢复和程序重启后继续沿用原查询码。
- 云端不可用时保留本地配置和日志，恢复后可以重试上传。
- 修改通道配置快照或关闭后重新开启上传时产生新查询码。
- 云端能够按查询码汇总全部批次和业务字段。
- 未上传云端的历史文件可以只删除记录，或同时删除本地文件。

本文不验收 AI 日志分析效果。

## 2. 测试环境

### 2.1 必备条件

- Windows 测试电脑一台。
- COM24 串口设备，且设备能够持续输出日志。
- LogMaster 采集端测试版本。
- 可访问的 LogMaster 云平台。
- 云端 PostgreSQL 中已经存在测试项目和上传账号。
- 采集端使用的上传 Token 与云端 `LOGMASTER_UPLOAD_TOKEN` 一致。
- 云端 `LOGMASTER_UPLOAD_OWNER_OPEN_ID` 对应数据库中已经存在的用户。

不要只根据采集端配置中写有 `COM24` 判断设备存在。测试前必须在 Windows 设备管理器或采集端端口列表中确认 COM24 当前可见。

### 2.2 建议测试数据

| 项目 | 建议值 |
| --- | --- |
| 串口 | COM24 |
| 项目 | DR5800，或云端已有的其他项目 |
| 版本 | MANUAL-E2E-V1 |
| 测试任务 | 连续上传手动测试 |
| 上传人 | 手动测试人员姓名 |
| 分段时间 | 10 秒 |
| 波特率 | 按设备实际值，示例为 115200 |

测试前记录采集端版本、云端版本、测试人和测试时间。

## 3. 启动环境

### 3.1 使用已部署云平台

1. 在浏览器打开云平台。
2. 确认页面可以正常加载。
3. 访问云端健康接口：`<云端地址>/api/health`。
4. 预期返回 `code=0`，并且 `data.status` 为 `ok`。
5. 在采集端“设置 > 云端上传”中确认后端地址正确。

采集端中的后端地址为只读项。如果地址错误，应修改实际使用的运行配置后重启采集端，不要只修改界面显示。

### 3.2 本机启动云平台

仅在开发或隔离测试电脑上执行，不能把生产数据库用于故障模拟。

```powershell
Set-Location D:\Downloads\LogMaster
$env:DATABASE_URL="postgres://<用户名>:<密码>@127.0.0.1:5432/logmaster?sslmode=disable"
$env:LOGMASTER_UPLOAD_TOKEN="<测试 Token>"
$env:LOGMASTER_UPLOAD_OWNER_OPEN_ID="<数据库中已有用户的 Open ID>"
go run .
```

在另一个 PowerShell 窗口检查：

```powershell
Invoke-RestMethod http://127.0.0.1:8080/api/health
```

预期结果：

- 云端监听 `8080`。
- 健康接口返回 `code=0` 和 `status=ok`。
- 云端启动日志没有数据库迁移失败或端口占用错误。

### 3.3 启动采集端

从设置了上传 Token 的 PowerShell 窗口启动采集端：

```powershell
$env:LOGMASTER_UPLOAD_TOKEN="<与云端一致的测试 Token>"
Set-Location D:\LogMaster\LogMaster\agent
.\bin\LogCollector-0.0.7.exe
```

如果当前测试包名称不同，使用实际生成的 `LogCollector-<版本>.exe`。

## 4. 基础配置检查

### 用例 01：未开启上传时的按钮名称

操作步骤：

1. 选择 COM24。
2. 打开通道配置。
3. 关闭“上传云端”。
4. 修改任意本地配置。

预期结果：

- 底部按钮名称为“保存通道配置”。
- 可以只保存本地通道配置。
- 不弹出查询码。

### 用例 02：上传人为必填项

操作步骤：

1. 开启“保存本地日志”。
2. 开启“上传云端”。
3. 选择项目并填写版本。
4. 清空上传人，或只输入空格。
5. 尝试保存。

预期结果：

- 界面提示开启云端上传前必须填写上传人。
- 不向云端创建上传会话。
- 不产生查询码。
- 按钮不会显示为已经满足上传条件的状态。

### 用例 03：上传配置完整时的按钮名称

操作步骤：

1. 开启本地保存和云端上传。
2. 选择项目。
3. 填写版本。
4. 填写上传人。

预期结果：

- 按钮名称变为“保存上传/通道配置”。
- 测试任务允许为空。

## 5. 创建上传会话

### 用例 04：首次保存并取得查询码

操作步骤：

1. 为 COM24 填写建议测试数据。
2. 点击“保存上传/通道配置”。
3. 等待云端响应。

预期结果：

- 弹窗标题为“上传配置已保存”。
- 弹窗显示一个 10 位查询码。
- 查询码由大写字母和数字组成。
- 上传队列后续显示该查询码。
- 没有出现“上传失败，请重试”。

需要留存：

- 查询码截图。
- 通道配置截图。
- 测试项目、版本、测试任务和上传人。

### 用例 05：重复保存相同配置

操作步骤：

1. 记录用例 04 的查询码。
2. 不修改任何配置，再次保存相同上传配置。

预期结果：

- 仍使用原查询码。
- 云端不会创建第二个上传会话。
- 不会把已有文件重复上传。

## 6. 连续多批上传

### 用例 06：同一串口上传至少两个批次

操作步骤：

1. 在“设置”中把日志分段时间调整为 10 秒，保存后按界面提示重启采集端。
2. 连接 COM24。
3. 开始采集。
4. 确认实时日志区域持续出现设备真实输出。
5. 保持采集至少 25 秒，使采集端形成至少两个日志文件。
6. 打开“上传队列”。

预期结果：

- 本地日志目录中至少存在两个非空日志文件。
- 上传队列中至少有两个已上传批次。
- 如具备云端数据库或服务日志权限，确认每个批次的 `client_request_id` 不同。
- 这些批次显示完全相同的查询码。
- 状态最终变为已上传，不是 `uncertain` 或失败。

如果设备输出量很小，应延长采集时间，不能用空文件作为通过依据。

### 用例 07：云端按查询码汇总

操作步骤：

1. 在云平台查询页面输入用例 04 的查询码。
2. 或调用：

```powershell
$code = "<查询码>"
$result = Invoke-RestMethod "<云端地址>/api/query/$code"
$result.data | ConvertTo-Json -Depth 6
```

预期结果：

- `query_code` 与采集端显示一致。
- `batch_count` 大于或等于 2。
- `total_files` 大于或等于 2。
- `processed_files` 最终等于 `total_files`。
- `status` 最终为 `completed`。
- `project_name`、`version`、`test_task_name` 和 `uploader_name` 与首次保存配置一致。
- `batches` 中至少包含两个不同的 `upload_id` 和 `task_id`。

## 7. 中断与恢复

### 用例 08：关闭串口但继续上传

操作步骤：

1. 采集出尚未完成上传的文件。
2. 点击关闭串口。
3. 选择“关闭串口，继续上传”。
4. 等待队列处理完毕。
5. 重新打开 COM24，并继续采集出新文件。

预期结果：

- 关闭串口后，已有文件继续上传。
- 重新连接后不创建新查询码。
- 新文件仍归属于原查询码。

### 用例 09：暂停上传后恢复

操作步骤：

1. 关闭串口时选择停止上传。
2. 确认待上传批次保持在本地，不继续发送。
3. 重新打开通道，并保持云端上传配置不变。
4. 恢复上传。

预期结果：

- 暂停期间不丢失本地文件。
- 恢复后继续处理原队列。
- 查询码不改变。
- 已上传文件不重复上传。

### 用例 10：程序重启后沿用查询码

操作步骤：

1. 记录当前查询码。
2. 正常关闭采集端。
3. 使用相同配置目录重新启动采集端。
4. 打开 COM24 并继续采集新日志。
5. 等待新批次上传完成。

预期结果：

- 重启后通道仍保存原上传会话状态。
- 新批次显示原查询码。
- 云端查询结果中的 `batch_count` 和 `total_files`继续增加。

## 8. 配置变更与新查询码

### 用例 11：修改配置快照后创建新会话

操作步骤：

1. 记录当前查询码 A。
2. 修改版本，例如从 `MANUAL-E2E-V1` 改为 `MANUAL-E2E-V2`。
3. 点击“保存上传/通道配置”。
4. 记录新弹窗中的查询码 B。
5. 继续采集并上传一个新批次。

预期结果：

- 查询码 B 与查询码 A 不同。
- 新批次只出现在查询码 B 的结果中。
- 查询码 A 仍可查询旧批次。
- 查询码 A 的业务字段保持旧版本，查询码 B 显示新版本。

串口参数、项目、版本、测试任务、上传人、备注、场景或关键字选择等会话快照发生变化时，都应按新配置创建会话。

### 用例 12：关闭上传后重新开启

操作步骤：

1. 记录当前查询码。
2. 关闭“上传云端”并保存。
3. 确认按钮恢复为“保存通道配置”。
4. 再次开启云端上传并保存。

预期结果：

- 关闭上传时不再为新文件排队上传。
- 重新开启后创建新查询码。
- 不复用关闭前的查询码。

## 9. 云端失败与重试

### 用例 13：创建会话失败时保存本地并暂停上传

本用例只能在隔离测试环境执行。不得通过停止生产云端服务进行测试。

操作步骤：

1. 在隔离环境中停止云端进程，或把测试网络临时断开。
2. 修改版本，确保本次保存需要创建新会话。
3. 点击“保存上传/通道配置”。
4. 在云端仍不可用时继续采集并形成一个本地文件。

预期结果：

- 本地通道配置保存成功。
- 弹窗显示“上传已暂停”和“上传失败，请重试”。
- 不显示查询码。
- 本地日志正常保存。
- 文件保留在待上传队列，不会被标记为已上传。
- 采集端不会无查询码向云端发送文件。

### 用例 14：恢复云端后重试

操作步骤：

1. 恢复云端服务和网络。
2. 确认健康接口恢复正常。
3. 不修改业务配置，再次点击“保存上传/通道配置”。
4. 等待积压文件上传。

预期结果：

- 本次返回查询码。
- 失败期间产生的积压文件绑定到该查询码。
- 积压文件恢复上传并最终完成。
- 多次点击重试不会生成多个查询码。

## 10. 历史文件删除

### 用例 15：只删除历史记录

操作步骤：

1. 关闭 COM24 的云端上传。
2. 采集并保存一个新的本地日志文件。
3. 在“历史文件”中找到状态为“仅本地”的记录。
4. 记录文件路径，并确认文件当前存在。
5. 点击删除，选择“只删除记录”。

预期结果：

- 历史列表中不再显示该记录。
- 本地磁盘中的日志文件仍然存在。
- 没有向云端发送删除请求。

### 用例 16：同时删除本地文件

操作步骤：

1. 再生成一个未上传的本地日志文件。
2. 在历史文件中点击删除。
3. 选择“同时删除本地文件”。

预期结果：

- 历史记录被删除。
- 对应本地日志文件被删除。

### 用例 17：已进入上传流程的文件不可删除

操作步骤：

1. 找到状态不是“仅本地”的记录，例如待上传、上传中、已上传或待核对。

预期结果：

- 不显示本地历史删除按钮，或后端拒绝删除。
- 已上传云端的数据不受影响。

## 11. 异常判定

出现以下任一情况，测试判定为失败：

- 开启上传后可以在上传人为空时保存并上传。
- 同一连续上传活动的不同批次出现不同查询码。
- 程序重启后无配置变更却生成新查询码。
- 修改版本后仍继续使用旧查询码。
- 云端失败时本地配置或日志丢失。
- 没有查询码的批次被发送到云端。
- 云端查询只返回一个批次，实际已经上传多个批次。
- 项目、版本、测试任务或上传人与采集端配置不一致。
- 同一批次因为重试在云端产生重复记录。
- `processed_files` 大于 `total_files`，或完成后两者不相等。
- 已上传历史文件仍可从采集端执行本地删除操作。

如果请求已经发出但采集端没有收到完整响应，应记录为“待核对”或 `uncertain`，不能直接反复重传。

## 13. 最终通过标准

只有同时满足以下条件，才能判定连续上传功能通过：

- COM24 确实被 Windows 识别并产生真实日志。
- 日志在本地形成至少两个非空文件。
- 两个以上批次携带同一个查询码上传成功。
- 云端查询按该查询码聚合全部批次和正确业务字段。
- 暂停、断开恢复和程序重启不更换查询码。
- 配置变更或关闭后重新开启上传会创建新查询码。
- 云端失败时本地保存并暂停，恢复后能够继续上传积压文件。
- 未上传历史记录的两种删除方式均符合预期。
