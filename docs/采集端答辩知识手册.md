# LogMaster 采集端答辩知识手册

> 适用版本：LogCollector 0.0.10
>
> 整理日期：2026-08-28
>
> 用途：项目答辩、功能演示、技术问答和现场故障说明

## 1. 一分钟介绍

LogMaster 采集端是运行在 Windows 挂测机上的桌面客户端。它从多个嵌入式设备的串口实时读取日志，将日志优先写入本地文件，再通过 SQLite 队列可靠上传到日志分析平台；同时按本地关键字规则识别异常，并在界面上展示采集、命中和上传状态。

答辩时建议这样概括：

> 我们把采集端设计成“采集、存储、上传解耦”的本地优先系统。串口负责持续产生数据，文件负责保全原始证据，SQLite 负责记录上传状态，平台负责集中查询和分析。网络或界面出现问题时，不会反过来阻塞串口采集。

## 2. 项目解决的问题

| 现场问题 | 采集端解决方案 |
| --- | --- |
| 手工导出日志效率低且容易漏数据 | 串口实时采集，按会话和文件自动保存 |
| 多台设备同时挂测难以管理 | 端口动态发现，每个串口独立采集和重连 |
| 断网时日志无法上传 | 本地文件优先，SQLite 持久化待上传队列 |
| 异常日志难以快速定位 | 关键字/正则匹配、命中计数和命中行记录 |
| 上传失败只有一句“失败” | 滚动诊断日志、错误分类、待核对状态和重试入口 |
| 长时间运行磁盘容易失控 | 磁盘上限、预警、已上传文件保留策略和清理任务 |

## 3. 系统架构与数据流

```text
串口设备
   │ 读取字节流、解码、按换行或空闲帧分段
   ▼
Go 采集核心（每串口独立生命周期）
   ├── 实时事件 → Wails IPC → Vue 3 界面
   ├── 日志行 → 分段文件（SHA-256、序号、时间范围）
   ├── 日志行 → 关键字/正则匹配 → 命中记录
   └── 文件封口 → SQLite 上传队列 → GZIP + multipart HTTP
                                      │
                                      ▼
                              日志分析平台
```

一条日志的生命周期：

1. 串口发现并打开，按照编码和串口参数读取数据。
2. 以换行或空闲帧边界形成逻辑日志，生成采集时间和递增序号。
3. 同时推送界面、写入本地分段文件、交给关键字匹配器。
4. 文件达到时间或大小条件后封口，计算 SHA-256 并进入上传队列。
5. Worker 压缩并上传；成功、失败和响应未知分别进入对应状态。

## 4. 技术栈与职责

| 层次 | 技术 | 选择理由 |
| --- | --- | --- |
| 桌面壳 | Wails v2 + WebView2 | Go 与界面同进程，安装包小，适合 Windows 挂测机 |
| 界面 | Vue 3 | 组件化展示通道、日志和队列状态 |
| 采集核心 | Go goroutine、context、channel | 适合多串口并发和生命周期控制 |
| 串口 | `go.bug.st/serial` | 统一 Windows 串口访问 |
| 本地数据库 | SQLite（`modernc.org/sqlite`） | 队列状态持久化，纯 Go、无需 CGO |
| 配置 | YAML + JSON | 便于现场维护和程序设置持久化 |
| 上传 | HTTP multipart + GZIP | 与平台接口兼容，降低带宽占用 |

## 5. 核心设计决策

### 5.1 为什么文件优先而不是直接上传？

串口日志是持续流，网络不是稳定条件。先落盘可以把采集速度和网络速度解耦：网络中断时继续采集，恢复后由队列补传；同时本地文件保留了可审计的原始证据。直接边采边传一旦连接断开，难以确定已发送范围，容易丢失或重复。

### 5.2 为什么每个串口独立管理？

每路串口可能有不同波特率、编码、断开时间和日志速率。独立 goroutine、独立 context 和独立状态可以做到单路重连、单路停止，不让一台设备的异常拖住其他设备。当前代码安全上限为 64 路，但正式稳定性验收以实际测试报告为准，不把“上限”表述成“已验证吞吐”。

### 5.3 为什么界面日志允许丢弃？

界面只是观察窗口，不是数据源。实时事件采用非阻塞推送，前端卡顿时可以丢弃旧的展示事件，但同一行仍优先写入本地文件。这样避免 UI 渲染反向阻塞串口读取。

### 5.4 为什么使用 SQLite 队列？

内存队列重启即丢失，单纯扫描文件又无法准确记录重试次数、请求结果和人工核对信息。SQLite 保存批次、文件摘要、上传 ID、任务 ID、错误原因和状态，支持崩溃恢复、查询和运维审计。

### 5.5 为什么使用 SHA-256？

文件封口时对原始内容计算 SHA-256，并保存大小、设备编号、序号范围和时间范围。平台或人工核对时不能只看文件名，摘要可以确认本地文件与平台文件是否为同一份内容。

## 6. 上传可靠性设计

### 6.1 上传状态

| 状态 | 含义 | 处理方式 |
| --- | --- | --- |
| `pending` | 等待上传 | Worker 自动处理 |
| `uploading` | 已被 Worker 取出 | 重启时按时间窗口恢复 |
| `uploaded` | 平台明确确认 | 可按保留策略清理本地文件 |
| `uncertain` | 请求可能已到达，但确认响应未知 | 暂不盲目重传，先人工核对 |
| `dead` | 达到最大重试次数或确定失败 | UI 展示原因，人工重新上传 |

### 6.2 为什么不能对 `uncertain` 自动重传？

请求可能已经被平台接收，只是客户端没有拿到响应。当前 V1 后端不宣称 exactly-once，也没有足够的服务端幂等保证；此时无条件重传可能产生重复任务。因此采集端保留原始 `Idempotency-Key`、文件 SHA-256 和错误信息，要求先在平台核对，再决定重传或确认已上传。

### 6.3 成功如何判定？

不能只以“HTTP 请求没有报错”为成功。当前契约要求同时检查 HTTP `202`、业务 `code=0`、非空 `upload_id`、非空 `task_id`，并核对返回文件数量与本批文件数一致；会话模式还要核对查询码和请求关联信息。只有全部满足才将批次标记为 `uploaded`。

### 6.4 关闭串口时怎么办？

用户可以选择“关闭串口，继续上传”或“关闭串口，停止上传”。前者停止产生新日志，但已封口文件继续上传；后者暂停该通道尚未开始的上传任务。已发出的请求不会被粗暴取消，其他通道不受影响。

## 7. 关键字与异常识别

- 支持普通包含和正则表达式规则，可配置大小写敏感、级别和模块。
- 规则在采集端本地执行，不依赖网络，适合断网挂测。
- 命中记录包含规则、时间、序号和原始行，界面提供命中次数和明细。
- 长时间运行会对命中文本和历史记录做长度、时间保留控制，避免数据库无限增长。
- AI 分析不是采集端采集链路的前置条件；采集端先保证原始日志和规则命中证据完整，平台侧再按需分析。

## 8. 配置与日常演示

推荐演示顺序：

1. 启动程序，点击扫描，展示 Windows 当前可用串口。
2. 选择一个串口，配置波特率、数据位、停止位、校验位和编码，保存通道配置。
3. 打开“本地保存”，按需打开“上传云端”和关键字匹配。
4. 点击开始采集，展示实时日志、已接收行数、规则命中数、重连次数和 UI 丢弃数。
5. 等待文件封口，打开上传队列，展示文件数量、进度、查询码和状态。
6. 模拟断网，证明日志继续落盘且队列进入 `pending`；恢复网络后观察补传。
7. 模拟响应未知，展示 `uncertain`，说明先核对后重传的原因。
8. 结束采集，打开历史记录和诊断日志，说明证据如何留存。

现场配置重点：

- 后端地址、项目、版本和上传鉴权按现场环境填写；Token 通过请求头/环境变量提供，不写入普通配置和日志。
- 默认新通道本地保存开启、云端上传关闭，避免未确认项目和上传人时误传。
- 默认日志目录和 SQLite/spool 目录应放在有足够空间且服务账号可写的位置。
- 目标机器需要 Microsoft Edge WebView2 Evergreen Runtime。

## 9. 高频答辩问题与标准回答

**问：断网会不会丢日志？**

答：采集和上传解耦，文件先落盘；断网时批次进入 SQLite 的 `pending`，网络恢复后继续上传。只有磁盘满、权限失败或人为删除本地文件才可能影响保全，所以现场还要配合磁盘监控。

**问：前端卡死会不会影响采集？**

答：不会。前端事件是非阻塞观察通道，采集、落盘和上传 Worker 不依赖前端渲染完成；界面最多保留有限行数，防止浏览器内存无限增长。

**问：如何避免重复上传？**

答：本地通过文件路径、批次状态和请求 ID避免重复排队；明确成功后才标记完成。响应未知时不自动重传，因为 V1 后端幂等能力不足，采用 SHA-256、大小、设备和时间范围人工核对。

**问：为什么不用 Electron？**

答：采集端需要长时间低资源运行。Wails 复用系统 WebView2，Go 直接承载串口、文件和队列逻辑，部署体积和内存开销更适合挂测机。

**问：串口没有换行符怎么办？**

答：解码层支持按空闲间隔分帧，并设置最大帧长度；达到空闲边界或长度上限就封口，避免日志长期滞留在内存。

**问：为什么要做文件切割？**

答：按时间或大小切割，将无限流转换为有限上传单元。单个文件失败可以独立重试，历史查询、摘要核对和磁盘清理也更容易。

**问：64 路是否已经通过验收？**

答：64 路是代码安全上限和动态能力，不等于所有环境都完成 64 路压力验收。当前 V1 的稳定性结论应以测试报告中的路数、吞吐、设备和 Windows 环境为准；答辩时应明确区分“支持上限”和“已验证范围”。

**问：上传失败为什么不自动创建项目？**

答：项目属于平台治理数据，采集端不应在拼写错误或权限不足时隐式创建。当前做法是透出平台的具体错误，交由管理员维护项目和版本。

## 10. 安全、稳定性与可观测性

- 本地分析服务默认监听 `127.0.0.1`，避免无认证暴露到局域网。
- 上传使用 Bearer Token；Token、API Key 和完整 Prompt 不写入配置示例、任务字段或诊断日志。
- 串口、文件、数据库和网络均使用 context 控制退出，关闭窗口时释放串口并等待后台任务收尾。
- SQLite 使用 WAL、完整同步和单写连接，降低并发状态错乱风险。
- 采集端诊断日志位于 `%APPDATA%\LogMaster\logs\collector.log`，单文件滚动并保留备份，记录启动、退出、上传错误、重试和异常堆栈。
- 已上传文件可按保留时长清理；未上传文件禁止在没有审批和核对的情况下删除。

## 11. 已验证内容与当前边界

已具备的交付证据包括：Go 全量测试、前端测试、生产构建、Windows Wails 打包，以及 COM24 实机的日志读取、文件落盘、上传和查询码回显测试。长时稳定性结论必须引用对应测试报告，不应只口头承诺。

当前边界：

- V1 不宣称服务端 exactly-once；`uncertain` 必须人工核对。
- WebView2 是运行前置条件，单 EXE 不代表完全无依赖。
- 物理串口识别依赖驱动提供的 VID/PID、USB 序列号和物理位置质量。
- 磁盘阈值是应用保护，不替代操作系统级容量告警。
- 云端配置同步、在线升级、自动回滚和复杂 AI 分析不属于采集端核心 V1 交付边界。

## 12. 答辩禁区与应对原则

不要把“规划文档中的目标能力”说成“当前版本已经实现”；不要把“64 路代码上限”说成“64 路已完成性能验收”；不要承诺断电、磁盘损坏或平台故障下绝对零丢失；不要把 `uncertain` 说成失败，也不要在没有平台核对时承诺自动重传不重复。

遇到尚未验证的问题，建议回答：

> 这个能力在架构上已经预留，但当前版本的交付结论以现有测试报告为准。我们会先说明已验证范围、失败时的降级行为和后续验证计划，不把推测当成测试结果。

## 13. 结论

采集端的核心价值不是“把串口文字显示出来”，而是把不稳定的现场日志流转换为可追溯、可恢复、可核对的证据链：串口采集保证实时性，本地文件保证原始数据，SQLite 保证任务状态，上传协议保证平台协同，诊断日志保证问题可定位。答辩时围绕这条主线展开，技术细节都能回到可靠性和现场可用性。
